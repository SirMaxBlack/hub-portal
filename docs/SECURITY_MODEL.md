# Модель защиты HUB Portal

## Назначение

HUB Portal является внешним шлюзом к внутренним web-сервисам. Его задача — не
только показать карточки, а не допустить запрос к upstream до проверки:

- глобального IP/CIDR;
- действующей серверной сессии;
- активности пользователя;
- обязательной смены временного пароля;
- персонального IP/CIDR;
- роли администратора или права на конкретный сервис;
- состояния публикации сервиса.

Downstream может дополнительно показывать собственную форму входа. HUB не
заменяет её и не хранит пароль от внутреннего приложения.

## 1. Внешний периметр nginx

- наружу публикуется nginx, а не Gunicorn и не MariaDB;
- TLS завершается nginx;
- HTTP перенаправляется на HTTPS в domain-режиме;
- применяются security headers и HSTS;
- каждый reverse proxy имеет отдельный явный vhost;
- перед proxy выполняется `auth_request` в Django;
- текущий nginx-конфиг проверяется через `nginx -t` до reload;
- при ошибке применения сервисного конфига helper возвращает предыдущую версию.

Установщик намеренно не создаёт глобальный catch-all vhost на shared server,
чтобы не перехватывать чужие сайты. Неизвестная DNS-запись сама по себе не
становится сервисом HUB.

## 2. Закрытый `auth_request`

nginx передаёт в `/internal/authz` исходный host, URL и cookie сессии. Endpoint
проверяет shared key `HUB_PORTAL_INTERNAL_AUTH_KEY`; внешний запрос без этого
ключа не должен получить доверенный ответ.

Ответы:

- `200` — запрос можно передать upstream;
- `401` — требуется вход;
- `403` — пользователь известен, но доступ запрещён;
- blocked/health condition — сервис не открывается.

Одной подделки URL, JavaScript или карточки во frontend недостаточно: решение
принимается backend для каждого прохода через nginx.

## 3. Сессии и cookie

- session data хранится сервером в MariaDB;
- срок сессии — 24 часа от момента входа и не продлевается каждым запросом;
- cookie имеет `HttpOnly`, `Secure` в HTTPS и `SameSite=Lax`;
- cookie domain задаётся только для необходимой общей зоны сервисов;
- nginx удаляет cookie HUB перед отправкой upstream, чтобы внутреннее приложение
  не получало сессионный идентификатор портала;
- пользователь и администратор могут завершать активные сессии через интерфейс.

## 4. Пароли и токены

- пароли хэшируются Argon2id и не восстанавливаются;
- временный пароль требует смены после входа;
- новый пароль не должен совпадать со старым;
- login token хранится как hash для проверки и отдельно шифруется для разрешённого
  показа владельцу/администратору;
- token plaintext не записывается в URL, audit metadata и frontend logs;
- ротация делает старый token недействительным;
- токен не отменяет IP/CIDR, active-state и права пользователя.

## 5. Ограничение ошибок входа

Для логина/пароля можно настроить число ошибок и время блокировки. Состояние
хранится сервером и проверяется только при авторизации.

Блокируется сочетание учётной записи и устойчивого server-side browser identity,
а не весь офисный IP. Это снижает риск массовой блокировки пользователей за NAT.
Администратор может снять ограничение для пользователя или сбросить все текущие
ограничения.

Вход по token не расходует password-attempt counter, но не обходится без других
проверок доступа.

Browser identity повышает стоимость повторных попыток, но не является абсолютной
идентификацией устройства. Злоумышленник с новым browser profile может получить
новую identity; защиту нужно сочетать с сильными паролями, CIDR/VPN и внешним
rate limiting.

## 6. Глобальный и персональный CIDR

Глобальный список определяет, откуда вообще можно увидеть форму входа и пройти к
защищённым сервисам. Персональный список дополнительно ограничивает вход под
конкретной учёткой.

```text
Глобальный CIDR разрешает адрес
AND
Персональный CIDR пользователя разрешает адрес или персональный список пуст
```

Пустой глобальный список означает unrestricted mode. Перед сохранением
restricted-списка обязательно включите адрес текущего администратора.

## 7. Роли и права сервисов

- обычный пользователь видит и открывает только назначенные сервисы;
- администратор видит все активные сервисы;
- прямой URL всё равно проходит backend authz;
- выдача роли администратора даёт полный административный доступ;
- отключение или архивация пользователя завершает сессии и отзывает token согласно
  операции управления.

## 8. Два типа карточек

### Reverse proxy

HUB контролирует каждый HTTP-запрос до upstream через nginx `auth_request`.

### Внешняя ссылка

HUB контролирует только факт открытия карточки. После redirect пользователь
покидает портал. HUB не может защищать, фильтровать или журналировать дальнейшие
действия на чужом сайте.

## 9. Health-check

Фоновый monitor проверяет только адреса, сохранённые администратором в БД. Ввод
не приходит от анонимного frontend-запроса, что ограничивает SSRF-поверхность.

Подтверждённо недоступный сервис блокируется как через карточку, так и при прямом
доступе. `unknown` не равен `down`: временное отсутствие свежей проверки не
должно автоматически уничтожать доступ.

## 10. Аудит и логи

MariaDB хранит бизнес-события портала:

- входы и ошибки входа;
- изменения пользователей, токенов и паролей;
- открытие карточки сервиса;
- административные действия;
- security deny.

Внутренние `assets`, heartbeat, polling и API downstream не записываются как
отдельные бизнес-события. Bot/scanner noise остаётся в отдельных nginx logs.

Очистка журнала включает maintenance lock: во время операции портал продолжает
работать, но новые audit-события и HUB project logs временно не записываются.

## 11. MariaDB и системные права

- MariaDB слушает только `127.0.0.1`;
- приложение работает как `hubportal`, а не root;
- env доступен `root:www-data` с режимом `0640`;
- GitHub token — `0600 root:root`;
- root helpers разрешены через узкие sudoers entries;
- сертификаты и private keys остаются в `/etc/letsencrypt` с системными правами.

## Домены сервисов и cookie zone

### Стандартная схема

Установщик по умолчанию создаёт безопасную дочернюю зону от полного hostname
портала:

```text
Портал:  hub.example.com
Сервисы: crm.hub.example.com, video.hub.example.com
Cookie:  .hub.example.com
Suffix:  .hub.example.com
```

Это рекомендуемая схема: cookie HUB не отправляется всем остальным поддоменам
`example.com`.

### Сервисы в другой подзоне того же базового домена

Желаемая схема:

```text
hub.example.com
a1.a.example.com
a2.a.example.com
a3.a.example.com
```

Одна DNS-запись недостаточна. Для текущей cookie-session архитектуры браузер
должен отправлять сессионную cookie и порталу, и сервисам. Общая зона здесь —
`.example.com`.

Технически понадобятся согласованные значения:

```dotenv
HUB_PORTAL_SERVICE_DOMAIN_SUFFIX=.a.example.com
HUB_PORTAL_SESSION_COOKIE_DOMAIN=.example.com
HUB_PORTAL_ALLOWED_HOSTS=hub.example.com,.a.example.com,127.0.0.1,localhost
HUB_PORTAL_CSRF_TRUSTED_ORIGINS=https://hub.example.com,https://*.a.example.com
```

После изменения env нужны restart приложения, создание managed vhost каждого
сервиса, сертификат и `hubctl doctor`.

Однако cookie `.example.com` получает более широкую область. Любой скомпрометированный
или недоверенный поддомен `example.com` увеличивает риск cookie tossing и атак на
общую cookie-зону. Безопаснее выделить отдельную зону:

```text
Портал:  portal.access.example.com
Сервисы: a1.access.example.com, a2.access.example.com
Cookie:  .access.example.com
Suffix:  .access.example.com
```

Текущий интерактивный installer автоматически использует `.<полный-host-портала>`.
Переход на sibling-домены после установки является ручной расширенной настройкой
и должен сначала проверяться на тестовой VM.

### Несвязанные домены

Если портал и сервис не имеют безопасной общей parent-domain, браузер не может
использовать одну host/domain cookie. Текущая версия не реализует отдельный SSO
relay между registrable domains. Не пытайтесь обходить это передачей session ID
в URL.

## 12. Что защита HUB не решает

- уязвимости самого downstream после разрешённого доступа;
- вредоносные действия администратора HUB;
- компрометацию браузера или устройства сотрудника;
- кражу пароля вне портала;
- сетевые атаки на upstream из внутренней сети в обход nginx;
- DDoS без внешнего anti-DDoS/WAF;
- безопасность внешней ссылки после redirect.

Если upstream доступен сотрудникам напрямую по внутреннему IP, HUB не может
контролировать такой обход. Ограничьте upstream firewall так, чтобы web-трафик к
нему принимался только от HUB/nginx и необходимых служебных узлов.

## 13. Рекомендуемый безопасный минимум

1. Domain/HTTPS mode.
2. Отдельная DNS-зона для HUB и сервисов.
3. Restricted CIDR или VPN для административного доступа.
4. Уникальные Argon2id-пароли и минимальное число администраторов.
5. Лимит ошибок входа.
6. Регулярный просмотр журнала.
7. Backup БД/env и snapshot VM перед update.
8. Закрытый `3306/tcp` и недоступный извне Gunicorn socket.
9. Firewall upstream: доступ только от HUB там, где это возможно.
10. Регулярное обновление ОС, nginx, MariaDB и HUB Release.
